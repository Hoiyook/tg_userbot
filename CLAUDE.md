# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a single-file Telegram userbot (`tg_userbot_final.py`) built on Telethon. It supports both Android/Termux and macOS/desktop (auto-detected via `is_termux()`) and watches the user's own **Saved Messages** ("me" chat):

1. Any media/file sent to Saved Messages is downloaded to `SAVE_FOLDER/<forward-source>/`.
2. Any Douyin (抖音) or Instagram link sent to Saved Messages is forwarded to `@DouYintg_bot`; the returned video is downloaded (preferring the "下载 MP4 HD" button) into separate subfolders (`Douyin/`, `Instagram/`).
3. Program-generated messages (commands, platform links, notifications) in Saved Messages are auto-deleted on an interval.
4. Media (video/photo/file) arriving in any chat on the download whitelist (managed with `/wl`, e.g. the @DouYintg_bot private chat) is downloaded to `SAVE_FOLDER/<chat-title>/`. Whitelisted chats only get media downloads — no commands, no platform-link parsing.
5. A companion bot account (`BOT_TOKEN`) runs in the same process and provides a clickable inline-button menu in its private chat (buttons are bot-only — verified that user accounts' buttons are not rendered by official clients). Any message (or `/start`) to the bot shows the main menu; callback presses execute the same service functions as the text commands and update the menu message in place. The bot chat is auto-cleaned too (keeps the newest menu message).
6. All downloads go through a persistent queue (`download_queue.json`): tasks are persisted before execution (media = message reference, platform links = full URL, so auto-clean of the original link message is harmless), survive restarts, and failed tasks park in a retry list for manual re-execution instead of being lost.

All comments, log output, and user-facing Telegram replies are in Chinese. The startup banner identifies the program as "TG Userbot v2.9".

## Running

```bash
pip install telethon        # only dependency
python tg_userbot_final.py  # first run prompts for phone number + code interactively
```

- Before the first run, create `tg_secrets.json` by copying the template: `cp tg_secrets.example.json tg_secrets.json`, then fill in `api_id`/`api_hash` (my.telegram.org) and, for the button menu, `bot_token`/`bot_username` (@BotFather → /token). This file is gitignored and stays local.
- Platform defaults: Termux uses `SAVE_FOLDER=/storage/emulated/0/Download/Nagram`; macOS/desktop uses `SAVE_FOLDER=~/Downloads/Nagram`. Override with the `TG_SAVE_FOLDER` environment variable. The session is `~/tg_downloader` on both platforms (each device logs in independently; do not copy one device's `.session` file to another and run both simultaneously). Delete the `.session` file to force re-login.
- Optional proxy: set `TG_PROXY=socks5://127.0.0.1:7890` (or `socks4://`, `http://`, optionally with `user:pass@`) to route Telegram connections through a proxy — required when running on networks that block Telegram. Parsed by `parse_proxy()` into a Telethon proxy tuple passed to `TelegramClient`. Requires `python-socks` installed (`pip install 'python-socks[asyncio]'`); without it Telethon silently ignores the proxy argument. Unset → direct connection (unchanged Termux behavior). Hiddify's local mixed proxy port on this Mac is `127.0.0.1:12334`.
- Transport: `TG_CONNECTION=full|obfuscated` selects the Telethon connection class. Default: `obfuscated` when a proxy is set (MTProto obfuscated transport, no TLS — fully async so stalls are recoverable via the login watchdog), `full` otherwise (TLS, original behavior). The `start_with_retry()` watchdog wraps `client.start()` in a 120s `wait_for` × 10 retries because Telethon's recv path has no read timeout and a stalled proxy node would otherwise hang forever (with `full`/TLS the blocking handshake makes even cancellation impossible).
- On macOS, the first run may trigger a system prompt asking to allow terminal access to the Downloads folder — allow it, or set `TG_SAVE_FOLDER` elsewhere.
- There is no build step or linter config. Unit tests (stdlib `unittest`, no extra deps) live in `test_whitelist.py` (whitelist), `test_menu.py` (button menu), `test_queue.py` (persistent queue), and `test_display.py` (final-filename/source-link display); run with `.venv/bin/python -m unittest discover -s . -p "test_*.py" -v`. Tests set `TG_SAVE_FOLDER` to a temp dir before importing the module (importing creates `SAVE_FOLDER` and opens the log file); they don't need `tg_secrets.json` (a missing one just yields empty defaults). A local `.venv` is used for Mac development: `python3 -m venv .venv && .venv/bin/pip install telethon 'python-socks[asyncio]'`.
- The bot account logs in with its own session file (`~/tg_downloader_bot.session`, separate from the user session). Its login is `start_with_retry(bot_client, bot_token=BOT_TOKEN)`; a failure logs an error but does not stop the userbot (menu just stays unavailable).

## Configuration

Non-secret settings are in the `配置区` block at the top of the file (platform detection via `is_termux()`/`IS_TERMUX`, `SESSION_NAME`, `SAVE_FOLDER`, `LOG_FILE`, `DOWNLOAD_RETRIES`, Douyin bot settings, auto-clean settings, `BOT_SESSION_NAME`). Settings should only be changed there. Platform branches must keep the Termux defaults intact. Runtime-adjustable settings persist to JSON files inside `SAVE_FOLDER` (`clear_time.json`, `thread_config.json`, `whitelist_config.json`).

**Real credentials are NOT hardcoded.** `api_id`/`api_hash`/`bot_token`/`bot_username` are read at import from `tg_secrets.json` (same directory as the script; override the path with `TG_SECRETS_FILE`). That file is gitignored and never committed — copy the committed template `tg_secrets.example.json` to `tg_secrets.json` and fill in real values (api_id/api_hash from my.telegram.org, bot_token/@bot from @BotFather). A missing `api_id`/`api_hash` aborts startup with a clear message; a missing `bot_token` only disables the button menu (downloading still works). Never commit real tokens to the repo — the public remote contains no secrets.

The bot is operated at runtime through Telegram commands sent to Saved Messages (not the shell): `/status`, `/folder`, `/logpath`, `/done [n] [keyword]` (download history: last n lines, default 10; fuzzy case-insensitive substring match on keyword, e.g. `/done 20 古风`), `/progress` (live progress of in-flight downloads), `/thread [n]` (show/set concurrent download count, 1–10, persisted), `/wl [list]` (list the download whitelist), `/wl add <id|@username>` (add a chat; alternatively reply to a forwarded message from that chat with `/wl add` — resolves `fwd_from`), `/wl del <id|list-index>` (remove), `/queue` (list the active download queue), `/queue del <n>` (remove a task), `/retry` (list the failed-task list), `/retry <n>` (manually re-execute a failed task), `/retry del <n>` (remove from the retry list), `/help`, `/clean` (delete stray `.download` temp files), `/clearmsg` (manually delete program messages), `/setcleartime 1m|off` (change auto-clean interval). Commands are defined in `handle_command`; the handler returns `False` for unknown `/` commands so they can fall through to download logic if they carry media. `/wl`, `/queue`, and `/retry` commands and replies are covered by the auto-clean whitelist (`is_wl_command`/`is_queue_command`/`is_retry_command` + reply prefixes in `CLEAN_NOTIFICATION_PREFIXES`).

Completed downloads are appended as one line per record to `DOWNLOAD_HISTORY_FILE` (`download_history.txt` inside `SAVE_FOLDER`), format: `时间 | 类型(普通/抖音) | 文件名 | 大小 | 来源`. Writes happen after the atomic `os.replace` in both `download_file` and `download_douyin_message`; both are serialized by `DOWNLOAD_LOCK` so appends never interleave. `/done` reads the last n lines via `get_history_lines` and truncates the reply to fit Telegram's 4096-char limit. `/done` commands and replies are included in the auto-clean whitelist (`is_done_command` + reply prefixes in `CLEAN_NOTIFICATION_PREFIXES`).

## Architecture

**Event loop rule (critical).** `client`, `DOWNLOAD_LOCK`, and `DOUYIN_LOCK` MUST be created inside `main()` (inside the running event loop), never at module level. On Python ≤3.9, asyncio primitives bind to the event loop that exists at construction time; a module-level client gets bound to a stale loop and `asyncio.run(main())` creates a new one, causing connections to establish but every request to hang forever with no error ("got Future attached to a different loop"). The Android/Termux install was unaffected only because its Python is ≥3.10, where primitives bind lazily. `client` is registered with `client.add_event_handler(new_message_handler, events.NewMessage())` in `main()` for the same reason.

**Single event entry point.** One `events.NewMessage()` handler passes the message through `classify_message_chat(chat_id, MY_ID, WHITELIST_CHATS)`: `("me", None)` for Saved Messages, `("chat", title)` for whitelisted chats, `(None, None)` otherwise (ignored). It then dispatches in this order, each branch returning early:

1. `/` commands → `handle_command` (only when the message came from `"me"` — whitelisted chats can never control the bot)
2. Douyin URLs in message text or link entities → `handle_media_links` → enqueue platform-link tasks (only for `"me"`)
3. Downloadable media → enqueue a media task (`enqueue_and_start`)

Downloads and Douyin processing are fired with `asyncio.create_task`, so the handler never blocks on network I/O.

**Download whitelist.** `WHITELIST_CHATS` (`{chat_id: title}`, chat ids are Telethon "marked" ids — negative for channels — obtained via `telethon.utils.get_peer_id`, which is what makes membership checks match `event.chat_id`) is loaded at startup from `whitelist_config.json` via `load_whitelist()` and mutated at runtime by `/wl` commands (persisted via `save_whitelist()`). For whitelisted chats, `download_file`'s `source_override` (the chat title) is passed through `resolve_download_source()`, which otherwise falls back to `get_forward_source()` — so whitelisted downloads land in `SAVE_FOLDER/<chat-title>/` while Saved Messages behavior is unchanged. Pure helpers (`classify_message_chat`, `parse_wl_command`, `is_wl_command`, `resolve_wl_del_key`, `entity_display_name`, whitelist load/save) are unit-tested in `test_whitelist.py`; the Telegram-facing `/wl` flow is verified by live testing.

**Button menu (bot account).** Buttons of any kind are bot-account-only — empirically verified (official clients render no keyboard at all on user-account messages). So a second client `bot_client` (created in `main()`, `create_bot_client()`, session `~/tg_downloader_bot.session`) logs in with `BOT_TOKEN` and hosts the menu. Callback payloads are `m:<action>[:<arg>]` (`encode_menu_data`/`parse_menu_data`, ≤64 bytes; `m:thread:5`, `m:wl_del:-100123`, …). `bot_message_handler` answers any owner message with the main menu, or a confirm-add flow when the owner forwards a message (forward source → `add_to_whitelist`); `bot_callback_handler` answers the query (`event.answer()`), dispatches via `handle_menu_action`, and edits the same message with the result. Both handlers check `event.chat_id == MY_ID` (owner-only). Command/service functions shared by text commands and the menu live in one section: `status_text`, `progress_text`, `done_reply_text`, `wl_list_text`, `apply_thread_limit`, `clean_temp_files`, `add_to_whitelist`, `del_from_whitelist` — `handle_command` is a thin dispatcher over them. Bot-chat auto-clean (`cleanup_bot_chat_once`, same loop/interval as Saved Messages cleanup): `plan_bot_chat_cleanup` deletes messages older than `CLEAN_MESSAGE_AGE_MINUTES` but always keeps the newest message that has buttons (the live menu). Menu-related pure functions are unit-tested in `test_menu.py`; the Telegram-facing menu flow is verified by live testing.

**Concurrency model.**
- `DOWNLOAD_SEMAPHORE` (custom `AdjustableSemaphore`, default limit 3) bounds concurrent downloads — normal files and platform videos share the pool. Unlike `asyncio.Semaphore`, the limit can change at runtime: `/thread n` calls `set_limit()` (range 1–10), persists to `thread_config.json`, and is loaded at startup via `load_thread_config()`. Reducing the limit does not cancel in-flight downloads; new tasks wait until the count drops below the new limit.
- `DOUYIN_LOCK` serializes platform URL processing (bot conversations must stay serialized — with `exclusive=False` conversations, parallel `get_response` calls would steal each other's bot replies).
- `PROCESSING_DOUYIN_IDS` (a set of message IDs) prevents duplicate triggers for the same message; IDs are discarded in a `finally`.
- Progress/attempt log lines include the target filename since parallel downloads interleave in the log.
- In-flight downloads are tracked in `ACTIVE_DOWNLOADS` (plain dict keyed by an incrementing id) via `register_download`/`update_download`/`unregister_download`; both download functions wrap their body in `try/finally` around the registration, and the `progress_callback` calls `update_download` before the throttled log line. `/progress` reads this dict directly (no lock needed — single-threaded event loop).

**Download pattern (shared by both flows).** Download to `final_path + ".download"`, then `os.replace()` to the final path for atomicity. Retries `DOWNLOAD_RETRIES` times with a 3-second delay, reconnecting the client between attempts if needed. `/clean` deletes leftover `.download` files.

**Persistent download queue.** All downloads run through a queue persisted in `download_queue.json` (`{"tasks": [...], "retry": [...]}`, file order = FIFO execution order). `enqueue_and_start()` appends a record (media: `{kind, chat_id, msg_id, source_override, label}`; platform link: `{kind, url, msg_id, label}` — the URL itself is persisted so auto-clean deleting the original link message doesn't matter), saves under `QUEUE_LOCK` (an `asyncio.Lock` created in `main()`), and spawns `execute_queued_task()`. **The queue layer deliberately does NOT acquire `DOWNLOAD_SEMAPHORE`** — `download_file`/`download_bot_video` already acquire it internally, and a second acquisition around them deadlocks when concurrency ≥ 2 (all slots held at the outer level while every task waits for an inner slot; regression-tested with a limit-1 semaphore). Actual file-download concurrency is still bounded by the internal semaphore; douyin bot conversations are serialized by `DOUYIN_LOCK` (and no longer occupy a download slot while waiting on the bot). Media tasks re-fetch the message via `client.get_messages(chat_id, ids=msg_id)` wrapped in a 30s `asyncio.wait_for` (`QUEUE_FETCH_TIMEOUT` — Telethon requests have no read timeout and a stalled proxy would otherwise wedge the queue forever); a deleted original message removes the task with a notification (permanent failure). Platform links re-run `process_platform_url(url, None, kind)` (now returns a bool). On success the record is removed; on failure it moves to `retry` with `attempts+1` and parks there — no automatic retry; the user re-triggers it via `/retry <n>` or the menu's ▶️ button (success removes it, failure leaves it in place). `EXECUTING` (set of record ids) prevents double-triggering. On startup `recover_queue_tasks()` re-spawns everything in `tasks` (interrupted downloads restart; leftover `.download` temp files are cleaned by the existing retry logic). Pure queue functions (`load_queue`, `save_queue`, `queue_enqueue`, `queue_fail_to_retry`, `queue_remove`, `queue_retry_success/failed`, `format_queue_text`, `format_retry_text`) and the deadlock regression test are in `test_queue.py`.

**Platform link flow (Douyin + Instagram).** The two platforms share one generalized pipeline parameterized by `kind` (`"douyin"`/`"instagram"`) via the `PLATFORM_CONFIG` dict (bot username, subfolder, timeouts, notification label/emoji). `extract_douyin_urls`/`extract_instagram_urls` both delegate to `extract_urls_by_pattern` with their own regex (douyin covers v./www./m./douyin.com; instagram covers instagram.com/instagr.am with optional www.). `process_platform_url` opens a `client.conversation()` with the configured bot, sends the URL, then iterates up to `max_responses` responses: `click_first_useful_button` prefers "下载 MP4 HD" keywords, otherwise any MP4/无水印/原视频 button (skipping MP3 buttons). The first direct-video response is kept as `fallback_response` and downloaded via `download_bot_video` only if the HD click never returns media or times out. Error keywords in bot text abort processing. `handle_media_links` dedupes by message ID (`PROCESSING_DOUYIN_IDS`) and processes douyin links before instagram ones; notification texts and history-record labels are generated from `PLATFORM_CONFIG`.

**Naming rules.** `sanitize_filename` strips Android/Windows-illegal characters; `unique_path` appends ` (1)`, ` (2)` on collision; `get_file_extension` infers extension from MIME when the original name lacks one. The whole naming decision lives in the pure `compute_final_filename(message)` (shared by `download_file` and queue display): normal downloads save as `<caption> - <filename>` in `SAVE_FOLDER/<forward-source-name>/` (source resolved via `get_forward_source` → `client.get_entity`); `get_caption` returns `""` for captionless messages (never `sanitize_filename("")`'s fallback "未命名文件", which used to prefix every captionless file). Meaningless names (未命名/UUID/32-hex, detected by `is_meaningless_filename`) are replaced with `媒体类型_时间戳` (or caption alone when present). Platform videos go to `SAVE_FOLDER/Douyin/` or `SAVE_FOLDER/Instagram/`, with the title parsed from the bot caption's `标题：...` line (hashtags kept), falling back to the first caption line, a meaningful Telegram filename, or `<kind>_<timestamp>.mp4`. A size sanity check logs a warning when the downloaded size is <98% of the message's declared size (client may show pre-transcode sizes).

**Display details.** `/queue`, `/retry`, and the menu views show each task's final filename (stored at enqueue time as `final_name`, unknown for platform links until parsed) plus a source line: channels/supergroups get a clickable `https://t.me/c/<id>/<msg_id>` link (`message_link()`, only `-100…` ids are linkable — private chats and Saved Messages have no link format and show `#msg_id` instead). `/progress` appends the same link per in-flight download (`register_download(..., link=…)`). Replies render URLs as plain text with `link_preview=False` (no markdown escaping needed).

**Auto-clean subsystem.** `cleanup_loop` runs as a background task; when the interval changes via `/setcleartime`, `CLEAR_TIME_CHANGED` (`asyncio.Event`) is set to wake the loop immediately instead of sleeping the full old interval. `is_cleanup_message` decides what to delete — exact command texts, `/setcleartime` commands and replies, any message containing a Douyin URL, or text starting with one of the `CLEAN_NOTIFICATION_PREFIXES` — so normal user content is never deleted. The auto-clean task only deletes messages older than `CLEAR_MESSAGE_AGE_MINUTES`, while manual `/clearmsg` has no age limit and deletes the invoking command message last. Note the latency: a message survives up to (interval + age threshold) before auto-deletion (defaults 1 + 1 = up to 2 minutes). Each cycle also runs `cleanup_bot_chat_once()` for the bot menu chat (same interval). `cleanup_saved_messages_once` logs a heartbeat line every cycle even when nothing is deleted, and both cleanups also run once immediately after startup.

**Logging.** Custom `tg_userbot` logger writes to both console and `LOG_FILE` (inside `SAVE_FOLDER`). Progress callbacks log every `PROGRESS_STEP` percent. Log lines are the primary debugging tool; the startup routine prints instructions on how to verify message reception (expect the "📨 Saved Messages 收到消息" line).

## 磁盘回收：媒体经 CloudDrive2 自动搬到 115（外部配置）

本地磁盘只留最近下载，**已完成的媒体**由 CloudDrive2（CD2，本机 WebDAV 端口 19798）的「备份」任务自动搬到 115 后删本地。这不是本仓库代码逻辑，是 CD2 侧的一次性运维配置，记录如下便于日后对照/排查：

- **备份任务**：源 = `SAVE_FOLDER`（macOS 为 `~/Downloads/Nagram`，CD2 界面里可能把家目录显示成 `/用户名/Downloads/Nagram`，以能看到媒体子文件夹为准）；目标 = `115open/Nekogram`。
- **文件过滤 = 白名单·扩展名**（媒体才搬，运行时文件天然免疫）：
  视频 `mp4 mkv mov avi wmv flv webm ts m4v mpg mpeg 3gp`；图片 `jpg jpeg png gif webp heic bmp tiff`；音频 `mp3 m4a ogg opus flac wav aac`。
- **完成规则 = 删除源文件**（真正释放磁盘的开关）。其余开关务必按此设置，顺序是先配好白名单再开删除源：
  - **删除规则（本地删文件时云端怎么处理）= 保留**。绝不能选「回收站/同步删除」，否则本地任何删除会把 115 上的备份副本一起清掉。
  - 替换规则 = 跳过（或历史版本）；实时监控开启。

安全原理：白名单外的一切（`download_history.txt`、`download_queue.json`、`download.log`、`whitelist_config.json`、`thread_config.json`、`clear_time.json`、`*.download`）不会进入备份 → 没有「完成后」→ 删除源规则不会碰它们。**设计取舍**：zip/rar/pdf 等归档类不在白名单，会一直留在本地（若也转发大量归档，磁盘仍会缓慢增长，需手动加后缀进白名单）。校验过一次真实运行：`Douyin`/`Instagram`/频道子文件夹的媒体被搬空删净、6 个运行时文件健在。

**.download 半成品**：中断的下载重启后是「删半成品、整文件重下」，不支持断点续传（见下载模式）。残留的 `.download` 不会被 CD2 搬走、也不被自动清理——`clean_temp_files()`（`/clean`）是唯一清理入口。正常情况下重启能自愈（任务已持久化，重下前删同名 temp）；出现孤儿 `.download` 的成因为：队列任务被移除后旧 temp 无人认领——原消息已删除被自动终结、`/queue del`/`/retry del` 清掉任务，或**命名逻辑跨版本变化**导致重启后算出的最终名与旧 temp 不同（实测案例：无 caption 文件旧版名 `未命名文件 - X.mp4`、新版名 `X.mp4`，旧半成品成死文件）。
