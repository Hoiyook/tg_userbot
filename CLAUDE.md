# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a Telegram userbot built on Telethon, structured as a standard flat package (`tg_userbot/`, 18 subsystem modules — see the Module index in Architecture). The repo root keeps only a thin run shell, `tg_userbot_final.py`, so the run command below and the `.claude` pkill rules stay keyed to that filename; the pre-refactor single file is preserved for rollback as `tg_userbot_final.py.bak_20260905`. It supports both Android/Termux and macOS/desktop (auto-detected via `is_termux()`) and watches the user's own **Saved Messages** ("me" chat):

1. Any media/file sent to (or forwarded into) Saved Messages is downloaded to `SAVE_FOLDER/<forward-source>/`. Retained media copies stay in Saved Messages (never auto-cleaned).
2. Any Douyin (抖音) or Instagram link sent to Saved Messages is relayed to the parse bot `@DouYintg_bot`; the bot's first direct-video reply is auto-forwarded (via the whitelist, item 4) into Saved Messages and downloaded from that retained copy under the generic naming — no `Douyin/`/`Instagram/` subfolders, no "下载 MP4 HD" button click.
3. Program-generated messages (commands, link relays, notifications) in Saved Messages are auto-deleted on an interval; real media (including the copies above) is never deleted.
4. Media (video/photo/file) arriving in any chat on the download whitelist (managed with `/wl`, e.g. the @DouYintg_bot private chat) is **forwarded to Saved Messages**, then downloaded from that retained copy into `SAVE_FOLDER/<source>/`. Whitelisted chats only get media relay — no commands, no platform-link parsing. The copy is a real `forward_to`, not a self-authored `send_file` copy: a forward's copy carries the system **「转发自 <来源>」 header**, which the user reads in Saved Messages to see the provenance and the target folder, and the download folder is resolved automatically from the copy's `fwd_from` at download time (`resolve_download_source()` → `get_forward_source()`) — re-forwarded albums keep landing under their true origin (e.g. `祂录（3D区）/`). Known trade-off (chosen by the user): a source message that carries inline buttons keeps those buttons on the forwarded copy, because Telegram forbids editing a forwarded message so they can't be stripped afterwards (live-verified: `EditMessageRequest` fails on forwarded copies). A forwarded copy can't gain a caption either, so **album members that carry no caption don't inherit text on the message itself** — instead the group caption is read once at relay time (`_maybe_album_caption` → `_fetch_group_caption`): a mixed media+photo album only carries text on one member, fetched from a ±10-id sibling window in the source chat and run through `pick_group_caption_text`; it is stored on the queue record as `album_caption`, and the download applies it as the naming caption — so grouped photos fall to `日期 相册标题 …` names instead of `photo_时间戳`. Source/folder resolution and caption inheritance are best-effort — failure only logs, never blocks the download. Albums are relayed as one unit, not member-by-member: same-`grouped_id` members are buffered ~1.5 s then forwarded in a **single** `forward_messages`, so Saved Messages keeps the album intact instead of N loose copies (see the unified-relay section).
5. A companion bot account (`BOT_TOKEN`) runs in the same process and provides a clickable inline-button menu in its private chat (buttons are bot-only — verified that user accounts' buttons are not rendered by official clients). Any message (or `/start`) to the bot shows the main menu; callback presses execute the same service functions as the text commands and update the menu message in place. The bot chat is auto-cleaned too (keeps the newest menu message).
6. All downloads go through a persistent queue (`download_queue.json`): media tasks are persisted before execution as message references (only `kind=media` — Saved Messages originals and whitelist-relayed copies), survive restarts, and failed tasks park in a retry list for manual re-execution instead of being lost.

All comments, log output, and user-facing Telegram replies are in Chinese. The startup banner identifies the program as "TG Userbot v2.9".

## Running

```bash
pip install telethon        # only dependency
python tg_userbot_final.py  # first run prompts for phone number + code interactively
```

- Before the first run, create `tg_secrets.json` by copying the template: `cp tg_secrets.example.json tg_secrets.json`, then fill in `api_id`/`api_hash` (my.telegram.org) and, for the button menu, `bot_token`/`bot_username` (@BotFather → /token). Optional machine-specific values go here too — the `cd2` segment (CloudDrive2 binary path + port + backup log dir, see the template) enables the menu's 【启动CD2】/【停止CD2】/【🗂 备份记录】 buttons. This file is gitignored and stays local.
- Platform defaults: Termux uses `SAVE_FOLDER=/storage/emulated/0/Download/Nagram`; macOS/desktop uses `SAVE_FOLDER=~/Downloads/Nagram`. Override with the `TG_SAVE_FOLDER` environment variable. The session is `~/tg_downloader` on both platforms (each device logs in independently; do not copy one device's `.session` file to another and run both simultaneously). Delete the `.session` file to force re-login.
- Optional proxy: set `TG_PROXY=socks5://127.0.0.1:7890` (or `socks4://`, `http://`, optionally with `user:pass@`) to route Telegram connections through a proxy — required when running on networks that block Telegram. Parsed by `parse_proxy()` into a Telethon proxy tuple passed to `TelegramClient`. Requires `python-socks` installed (`pip install 'python-socks[asyncio]'`); without it Telethon silently ignores the proxy argument. Unset → direct connection (unchanged Termux behavior). Hiddify's local mixed proxy port on this Mac is `127.0.0.1:12334`.
- Transport: `TG_CONNECTION=full|obfuscated` selects the Telethon connection class. Default: `obfuscated` when a proxy is set (MTProto obfuscated transport, no TLS — fully async so stalls are recoverable via the login watchdog), `full` otherwise (TLS, original behavior). The `start_with_retry()` watchdog wraps `client.start()` in a 120s `wait_for` × 10 retries because Telethon's recv path has no read timeout and a stalled proxy node would otherwise hang forever (with `full`/TLS the blocking handshake makes even cancellation impossible).
- On macOS, the first run may trigger a system prompt asking to allow terminal access to the Downloads folder — allow it, or set `TG_SAVE_FOLDER` elsewhere.
- There is no build step or linter config. Unit tests (stdlib `unittest`, no extra deps) live in `tests/`: `test_whitelist.py` (whitelist), `test_menu.py` (button menu), `test_queue.py` (persistent queue), `test_display.py` (final-filename/source-link/album-caption display), `test_cleanup.py` (cleanup predicate incl. retained-media-copy protection), and `test_platform_extract.py` (URL extraction regression); run from the repo root with `.venv/bin/python -m unittest discover -s tests -p "test_*.py" -v`. Tests set `TG_SAVE_FOLDER` to a temp dir before importing `tg_userbot` (importing the package creates `SAVE_FOLDER` and configures the logger once); they don't need `tg_secrets.json` (a missing one just yields empty defaults). A local `.venv` is used for Mac development: `python3 -m venv .venv && .venv/bin/pip install telethon 'python-socks[asyncio]'`.
- The bot account logs in with its own session file (`~/tg_downloader_bot.session`, separate from the user session). Its login is `start_with_retry(bot_client, bot_token=BOT_TOKEN)`; a failure logs an error but does not stop the userbot (menu just stays unavailable).

## Configuration

Non-secret settings live in `tg_userbot/config.py` (platform detection via `is_termux()`/`IS_TERMUX`, `SESSION_NAME`, `SAVE_FOLDER`, `LOG_FILE`, `DOWNLOAD_RETRIES`, Douyin/Instagram URL regexes + parse-bot username/labels (`PLATFORM_LINKS`), auto-clean settings, `BOT_SESSION_NAME`, the runtime JSON filenames, and the `AdjustableSemaphore` class). Settings should only be changed there. Platform branches must keep the Termux defaults intact. Runtime-adjustable settings persist to JSON files inside `SAVE_FOLDER` (`clear_time.json`, `thread_config.json`, `whitelist_config.json`).

**Real credentials are NOT hardcoded.** `api_id`/`api_hash`/`bot_token`/`bot_username` are read at import from `tg_secrets.json` in the **repo root** — computed as `REPO_ROOT` in `config.py` from the package's `__file__` (deliberately *not* the `tg_userbot/` package dir, which is where a naive `__file__`-relative lookup would land after the refactor); override the path with `TG_SECRETS_FILE`. That file is gitignored and never committed — copy the committed template `tg_secrets.example.json` to `tg_secrets.json` and fill in real values (api_id/api_hash from my.telegram.org, bot_token/@bot from @BotFather). A missing `api_id`/`api_hash` aborts startup with a clear message; a missing `bot_token` only disables the button menu (downloading still works). Never commit real tokens to the repo — the public remote contains no secrets. Machine-specific paths that reveal the local username also belong in this file, never in code — e.g. the optional `cd2` segment (binary path + port + log dir) that powers the menu's 【启动CD2】/【停止CD2】/【🗂 备份记录】 buttons.

The bot is operated at runtime through Telegram commands sent to Saved Messages (not the shell): `/status`, `/folder`, `/logpath`, `/done [n] [keyword]` (download history: last n lines, default 10; fuzzy case-insensitive substring match on keyword, e.g. `/done 20 古风`), `/progress` (live progress of in-flight downloads), `/thread [n]` (show/set concurrent download count, 1–10, persisted), `/wl [list]` (list the download whitelist), `/wl add <id|@username>` (add a chat; alternatively reply to a forwarded message from that chat with `/wl add` — resolves `fwd_from`), `/wl del <id|list-index>` (remove), `/queue` (list the active download queue), `/queue del <n>` (remove a task), `/retry` (list the failed-task list), `/retry <n>` (manually re-execute a failed task), `/retry del <n>` (remove from the retry list), `/help`, `/clean` (delete stray `.download` temp files), `/clearmsg` (manually delete program messages), `/setcleartime 1m|off` (change auto-clean interval). Commands are defined in `handle_command`; the handler returns `False` for unknown `/` commands so they can fall through to download logic if they carry media. `/wl`, `/queue`, and `/retry` commands and replies are covered by the auto-clean whitelist (`is_wl_command`/`is_queue_command`/`is_retry_command` + reply prefixes in `CLEAN_NOTIFICATION_PREFIXES`).

Completed downloads are appended as one line per record to `DOWNLOAD_HISTORY_FILE` (`download_history.txt` inside `SAVE_FOLDER`), format: `时间 | 类型(普通) | 文件名 | 大小 | 来源`. Since the unified-chain refactor all downloads (incl. douyin/IG video copies relayed into Saved Messages) go through `download_file`, so every record is type `普通` — the old platform type `抖音` and the `download_bot_video` writer are gone. Writes happen after the atomic `os.replace` in `download_file` (download.py); each calls `history.append_history`, a **lockless synchronous append** — single-line short writes in `"a"` mode under the single-threaded event loop are atomic, so no `DOWNLOAD_LOCK` exists (the real concurrency primitives are `DOWNLOAD_SEMAPHORE`, `QUEUE_LOCK`, `CLEAR_TIME_CHANGED`, all in `state.py`). `/done` reads the last n lines via `history.get_history_lines` and truncates the reply to fit Telegram's 4096-char limit. `/done` commands and replies are included in the auto-clean whitelist (`history.is_done_command` + reply prefixes in `CLEAN_NOTIFICATION_PREFIXES`).

## Architecture

**Module index.** All code lives in the `tg_userbot/` package. Importing any submodule bootstraps the package exactly once (`__init__.py` → `config.py` → `os.makedirs(SAVE_FOLDER)` + `log.configure(LOG_FILE)` at config's end), so every entry point (thin shell, tests) gets the same init. Roles:

- `app.py` — entry wiring: `create_client`/`create_bot_client`, `start_with_retry`, `new_message_handler` (the single event entry), `main()`. The **only** module that constructs loop-bound primitives; `main()` assigns the initial real value to every `state.*` global (runtime adjustments like `/thread n` still write `state.DOWNLOAD_CONCURRENCY`).
- `config.py` — read-only constants, secret loading, platform detection, URL regexes, parse-bot username/labels (`PLATFORM_LINKS`), `AdjustableSemaphore` class. Settings are changed here.
- `log.py` — shared `logger` + `configure()` (idempotent).
- `state.py` — the runtime-mutable globals (`client`, `bot_client`, `MY_ID`, `QUEUE`, `QUEUE_LOCK`, `EXECUTING`, `DOWNLOAD_SEMAPHORE`, `DOWNLOAD_CONCURRENCY`, `PROCESSING_DOUYIN_IDS`, `ACTIVE_DOWNLOADS`, `CLEAR_INTERVAL_SECONDS`, `CLEAR_TIME_CHANGED`, `WHITELIST_CHATS`, `_CD2_PROC`, …) as `None`/`{}` placeholders until `main()` fills them.
- Pure leaves `naming.py` (filename/caption/extension math, album-caption sibling text picker `pick_group_caption_text`), `sources.py` (chat/forward-source resolution, message links), `history.py` (download-history append/read, `is_done_command`).
- Feature modules `whitelist.py` (`/wl`), `thread.py` (`/thread`), `download.py` (`download_file` + in-flight progress registry), `platform.py` (Douyin/Instagram URL extraction + `relay_platform_links` — links are relayed to the parse bot, nothing is self-downloaded), `queue.py` (persistent queue pure functions + `enqueue_and_start`/`execute_queued_task`/`recover_queue_tasks`), `cleanup.py` (auto-clean loop, `clean_temp_files`, bot-chat cleanup), `text.py` (shared `status_text`/`progress_text`/`done_reply_text`/`wl_list_text`), `menu.py` (menu data codec + button builders), `cd2.py` (CD2 start/stop + backup records).
- Thin dispatchers `commands.py` (`handle_command`) and `bot.py` (`handle_menu_action`, `bot_message_handler`, `bot_callback_handler`).

Dependency rule: leaves (`config`/`log`/`state`/`naming`/`sources`/`history`) may be function-imported (`from .config import X`); runtime cluster modules import each other only as `from . import X` and call `X.func()` at call time. (The former sole module cycle `queue ↔ platform` was dissolved by the unified-chain refactor: `platform` no longer imports `queue`, and `queue` no longer imports `platform` — the call-time rule now just protects forward references generally.) Functions under test-patch (`save_whitelist`, `save_queue`, `get_forward_source`, `execute_queued_task`) keep bare-name calls inside their own module so `mock.patch.object(module, name)` stays visible.

**Event loop rule (critical).** Only `app.main()` — running inside `asyncio.run` — constructs loop-bound primitives: the `TelegramClient`s (`app.create_client`/`create_bot_client`), the `asyncio.Lock` (`QUEUE_LOCK`), `asyncio.Event` (`CLEAR_TIME_CHANGED`), and the `AdjustableSemaphore` (`DOWNLOAD_SEMAPHORE`). Every one of these lives in `state.py` as a `None`/empty placeholder until `main()` assigns a real value, so **no module ever constructs one at import time**. On Python ≤3.9, asyncio primitives bind to the event loop that exists at construction time; a module-level client would bind to a stale loop and `asyncio.run(main())` creates a new one, causing connections to establish but every request to hang forever with no error ("got Future attached to a different loop"). The Android/Termux install was unaffected only because its Python is ≥3.10, where primitives bind lazily. Runtime globals are read/written as `state.X` (never `from .state import X`); read-only constants may be top-level `from .config import X`. Handlers are registered on the client inside `main()` (`client.add_event_handler(new_message_handler, events.NewMessage())`) for the same reason.

**Single event entry point.** One `events.NewMessage()` handler passes the message through `classify_message_chat(chat_id, MY_ID, WHITELIST_CHATS)`: `("me", None)` for Saved Messages, `("chat", title)` for whitelisted chats, `(None, None)` otherwise (ignored). It then dispatches in this order, each branch returning early:

1. `/` commands → `handle_command` (only when the message came from `"me"` — whitelisted chats can never control the bot)
2. Douyin/Instagram URLs in message text or link entities → `platform.relay_platform_links` → send the link text to the parse bot (only for `"me"`)
3. Downloadable media → `"me"`: `enqueue_media` the original message; whitelisted chat: `relay_chat_media` forwards a copy to Saved Messages then `enqueue_media` that copy — single media immediately, album members batched into one grouped forward (forward failure falls back to downloading the original directly)

Media relay/enqueue and link relay are fired with `asyncio.create_task`, so the handler never blocks on network I/O.

**Download whitelist (unified relay).** `WHITELIST_CHATS` (`{chat_id: title}`, chat ids are Telethon "marked" ids — negative for channels — obtained via `telethon.utils.get_peer_id`, which is what makes membership checks match `event.chat_id`) is loaded at startup from `whitelist_config.json` via `load_whitelist()` and mutated at runtime by `/wl` commands (persisted via `save_whitelist()`). A whitelisted chat's media is **relayed** rather than directly downloaded: `relay_chat_media` (app.py) forwards the message to Saved Messages (`_forward_to_me` → bare `message.forward_to("me")`, deliberately **not** wrapped in `wait_for`), keeps the copy, and enqueues it (`chat_id=MY_ID`). A big album burst (~20 members forwarding at once) trips Telegram's forward FloodWait; Telethon auto-sleeps below its threshold and `_forward_to_me` catches the above-threshold `FloodWaitError` to sleep (≤120s) and retry — a `wait_for` cap would cancel that legal wait into a timeout and degrade the member to direct-download, splitting one album across two source folders (live-observed: several of the same album's members landed under `1仓鼠_3D区/` while the rest went to `祂录（3D区）/`). A real forward is used rather than a self-authored `send_file` copy so the Saved Messages copy keeps the system **「转发自 <来源>」 header** — the user reads it to tell which channel the content came from and where it will be saved; the folder is then resolved from the copy's own `fwd_from` at download time (`resolve_download_source()` → `get_forward_source()`), so a re-forwarded album still lands under its true origin (e.g. `祂录（3D区）/`) — no `source_override` needed. Known cost (user-approved): a source carrying inline buttons keeps them on the forwarded copy, since Telegram forbids editing forwarded messages. A forwarded copy also can't gain a caption, so album-caption inheritance is handled for **naming** instead of for the message: for a grouped member with no own text, `_maybe_album_caption` → `_fetch_group_caption` (a ±10-id sibling window in the source chat → `pick_group_caption_text`) reads the group caption once at relay time (cached per `grouped_id` in `_ALBUM_CAPTIONS` so the burst's other caption-less members don't each fire another `get_messages`); it's persisted on the queue record as `album_caption`, and both the enqueue-time display name and the download (`download_file(..., caption_override=record["album_caption"])`, shared by `queue._run_queued_task`) use it — `compute_final_filename(message, caption=…)` takes the caption override (a pure leaf change). Saved Messages originals get the same treatment via `_enqueue_me`. `enqueue_media` still accepts an explicit `source_link` (the original source's clickable link) for the queue display. If the forward fails (source forbids forwarding etc.), `relay_chat_media` catches the error and falls back to `enqueue_media` on the original message (source_override = chat title). Whitelist members still never get commands or platform-link parsing. **Album members are forwarded as one group, not N loose copies.** A Telegram album reaches the whitelist chat as N independent media events sharing one `grouped_id`; forwarding each on arrival would leave N separate messages in Saved Messages. Since 2026-09 `relay_chat_media` dispatches on that: no `grouped_id` → `_relay_single` (immediate single forward, the behavior above); has `grouped_id` → album coordinator `_relay_album_member`, which registers the member into per-`(chat_id, grouped_id)` state in `_ALBUM_RELAY` and has the first member start `_relay_album_group`. That task sleeps `_ALBUM_DEBOUNCE_SECONDS` (~1.5 s) so the burst's other member events land, then re-reads the **authoritative full member list** from the source chat (`_fetch_album_members`, a ±10-id window around the seen span filtered by `grouped_id` + `is_downloadable` — catching any member whose event didn't fire and locating the caption-holder) and forwards the whole group in **one** `client.forward_messages("me", members, from_peer=chat)` (`_forward_album_to_me`, same FloodWait retry as `_forward_to_me`) — Telegram re-groups the copies into a single album in Saved Messages. Each returned copy is enqueued (`chat_id=MY_ID`) sharing the group's source link; a copy carrying its own text keeps it, caption-less copies get the group caption as `album_caption` (naming inheritance unchanged). The coordinator keeps a `done` tombstone through `_ALBUM_SETTLE_SECONDS` (~5 s) then pops the entry, so a straggler member event is ignored rather than double-forwarding the group. Single media is unaffected (no delay). On failure the coordinator degrades to `_fallback_relay_each` (per-member `_relay_single`, the pre-batch behavior) so nothing is lost — batch forward error or empty source re-read both land there. Whether Telegram keeps an oversized album (>10 members) as one group or splits it across groups when forwarding into a user chat is server behavior and was still pending live verification on 2026-09-05. Pure helpers (`classify_message_chat`, `parse_wl_command`, `is_wl_command`, `resolve_wl_del_key`, `entity_display_name`, whitelist load/save) are unit-tested in `test_whitelist.py`; the Telegram-facing `/wl` flow is verified by live testing.

**Button menu (bot account).** Buttons of any kind are bot-account-only — empirically verified (official clients render no keyboard at all on user-account messages). So a second client `bot_client` (created in `main()`, `create_bot_client()`, session `~/tg_downloader_bot.session`) logs in with `BOT_TOKEN` and hosts the menu. Callback payloads are `m:<action>[:<arg>]` (`encode_menu_data`/`parse_menu_data`, ≤64 bytes; `m:thread:5`, `m:wl_del:-100123`, …). `bot_message_handler` answers any owner message with the main menu, or a confirm-add flow when the owner forwards a message (forward source → `add_to_whitelist`); `bot_callback_handler` answers the query (`event.answer()`), dispatches via `handle_menu_action`, and edits the same message with the result. Both handlers check `event.chat_id == MY_ID` (owner-only). Text commands and menu presses are both thin dispatchers — `commands.handle_command` and `bot.handle_menu_action` — over the same shared module functions: `text.status_text`/`progress_text`/`done_reply_text`/`wl_list_text`, `thread.apply_thread_limit`, `cleanup.clean_temp_files`, `whitelist.add_to_whitelist`/`del_from_whitelist`. Menu-only actions are 【启动CD2】/【停止CD2】 (`cd2`/`cd2_stop`) and 【🗂 备份记录】 (`bak`): the CD2 pair probe whether the local CloudDrive2 process is up on its management port and start or stop it via the configured standalone binary (start: detach + poll port; stop: match its PIDs by exact binary path and SIGTERM/SIGKILL); 备份记录 reads CD2's `backup.<日期>.log` to list media that was backed up and deleted locally. Config from the `cd2` segment of `tg_secrets.json`, never hardcoded — see the "磁盘回收" section. Bot-chat auto-clean (`cleanup_bot_chat_once`, same loop/interval as Saved Messages cleanup): `plan_bot_chat_cleanup` deletes messages older than `CLEAN_MESSAGE_AGE_MINUTES` but always keeps the newest message that has buttons (the live menu). Menu-related pure functions are unit-tested in `test_menu.py`; the Telegram-facing menu flow is verified by live testing.

**Concurrency model.**
- `DOWNLOAD_SEMAPHORE` (custom `AdjustableSemaphore`, default limit 3) bounds concurrent downloads — every media download (Saved Messages originals, whitelist-relayed copies, douyin/IG video copies) shares the pool. Unlike `asyncio.Semaphore`, the limit can change at runtime: `/thread n` calls `set_limit()` (range 1–10), persists to `thread_config.json`, and is loaded at startup via `load_thread_config()`. Reducing the limit does not cancel in-flight downloads; new tasks wait until the count drops below the new limit.
- `PROCESSING_DOUYIN_IDS` (a set of message IDs) prevents duplicate link relays for the same Saved Messages message (no conversation/no per-platform lock anymore — the parse bot is reached by plain `send_message`, so nothing needs serializing); IDs are discarded in a `finally`.
- Progress/attempt log lines include the target filename since parallel downloads interleave in the log.
- In-flight downloads are tracked in `ACTIVE_DOWNLOADS` (plain dict keyed by an incrementing id) via `register_download`/`update_download`/`unregister_download`; `download_file` wraps its body in `try/finally` around the registration, and the `progress_callback` calls `update_download` before the throttled log line. `/progress` reads this dict directly (no lock needed — single-threaded event loop).

**Download pattern (single shared path).** Every download goes through `download_file` (`download.py`): download to `final_path + ".download"`, then `os.replace()` to the final path for atomicity. Retries `DOWNLOAD_RETRIES` times with a 3-second delay, reconnecting the client between attempts if needed. The final path is claimed by `_reserve_final_path` before downloading: an in-process registry (`_RESERVED_FINAL_PATHS`, released in `finally`) plus `os.path.exists` disambiguation means two concurrent downloads that compute the same basename — e.g. same-album photos sharing one inherited `album_caption` and meaningless original names — never share a `.download` temp (which would make one fail with "临时文件不存在"). `/clean` deletes leftover `.download` files; `main()` also runs `clean_temp_files()` once at startup (safe — nothing is downloading yet) to catch orphaned temp files from abnormal exits or cross-version filename changes.

**Persistent download queue.** All downloads run through a queue persisted in `download_queue.json` (`{"tasks": [...], "retry": [...]}`, file order = FIFO execution order). There is exactly one task kind now — `media`, a message reference `{kind, chat_id, msg_id, source_override, label, final_name, source_link}` (Saved Messages originals and whitelist-relayed copies alike), with an optional `album_caption` (相册无文字成员继承到的同组说明) set only when a grouped member carries no own text, used by download/display naming. `enqueue_and_start()` appends the record, saves under `QUEUE_LOCK` (an `asyncio.Lock` created in `main()`), and spawns `execute_queued_task()`. **The queue layer deliberately does NOT acquire `DOWNLOAD_SEMAPHORE`** — `download_file` already acquires it internally, and a second acquisition around it deadlocks when concurrency ≥ 2 (all slots held at the outer level while every task waits for an inner slot; regression-tested with a limit-1 semaphore). Actual file-download concurrency is still bounded by the internal semaphore. Media tasks re-fetch the message via `client.get_messages(chat_id, ids=msg_id)` wrapped in a 30s `asyncio.wait_for` (`QUEUE_FETCH_TIMEOUT` — Telethon requests have no read timeout and a stalled proxy would otherwise wedge the queue forever); a deleted original message removes the task with a notification (permanent failure). On success the record is removed; on failure it moves to `retry` with `attempts+1` and parks there — no automatic retry; the user re-triggers it via `/retry <n>` or the menu's ▶️ button (success removes it, failure leaves it in place). `EXECUTING` (set of record ids) prevents double-triggering. On startup `recover_queue_tasks()` re-spawns everything in `tasks` (interrupted downloads restart; leftover `.download` temp files are cleaned by the existing retry logic). Historical `douyin`/`instagram` records that survived from before the unified-chain refactor hit the "unknown kind → remove + log" safety net in `_run_queued_task` (never crash or wedge; `QUEUE_KIND_LABELS` still renders them readably until removed). Pure queue functions (`load_queue`, `save_queue`, `queue_enqueue`, `queue_fail_to_retry`, `queue_remove`, `queue_retry_success/failed`, `format_queue_text`, `format_retry_text`) and the deadlock regression test are in `test_queue.py`.

**Platform link flow (Douyin + Instagram, relay-only).** `extract_douyin_urls`/`extract_instagram_urls` both delegate to `extract_urls_by_pattern` with their own regex (douyin covers v./www./m./douyin.com; instagram covers instagram.com/instagr.am with optional www.). When a Saved Messages message carries such a URL, `platform.relay_platform_links` (deduped per message id by `PROCESSING_DOUYIN_IDS`) simply sends the link text to the parse bot chosen per kind from `PLATFORM_LINKS` (douyin and instagram both use `@DouYintg_bot`; the dict carries only the bot username + a log label). Nothing is queued and nothing is self-downloaded: the parse bot's first direct-video reply is consumed by the whitelist relay (item 4 above) — because the parse bot's private chat is on the whitelist — and lands in Saved Messages for the normal media download. Best-effort, `_relay_kind_links` resolves the parse bot's entity and warns if it is not in `WHITELIST_CHATS` (its replies would otherwise never be forwarded); a send failure logs and notifies "me" with a `❌ 抖音链接处理失败`/`❌ Instagram链接处理失败` message (auto-cleaned).

**Naming rules.** `sanitize_filename` strips Android/Windows-illegal characters; `unique_path` appends ` (1)`, ` (2)` on collision; `get_file_extension` infers extension from MIME when the original name lacks one. The whole naming decision lives in the pure `compute_final_filename(message, caption=None)` (shared by `download_file` and queue display; the optional `caption` overrides the message's own text so album copies can inherit the group caption recorded as `album_caption`) — there is no platform-specific short name anymore, so douyin/IG video copies relayed into Saved Messages use the same generic naming. Since the relay refactor, every name starts with the **original message date prefix** `YY-MM-DD ` (`date_prefix(message)`, e.g. `26-09-05 `), which chronologically sorts each source folder and prevents same-caption collisions; the only exception is the pure fallback name `媒体类型_时间戳` (already carries the date). Files save as `<date> <caption> - <filename>` in `SAVE_FOLDER/<forward-source-name>/` (source resolved via `resolve_download_source()` → `get_forward_source` → `client.get_entity` from the message's `fwd_from` — whitelist-relayed forwards, Saved Messages originals, and user-forwarded copies alike all carry `fwd_from`, so every download resolves its folder the same way). `get_caption` returns `""` for captionless messages (never `sanitize_filename("")`'s fallback "未命名文件", which used to prefix every captionless file). Meaningless names (未命名/UUID/32-hex, detected by `is_meaningless_filename`) are replaced with `媒体类型_时间戳` (or caption alone when present — including an inherited `album_caption`, which flows through the same rule). A size sanity check logs a warning when the downloaded size is <98% of the message's declared size (client may show pre-transcode sizes).

**Display details.** `/queue`, `/retry`, and the menu views show each task's final filename (stored at enqueue time as `final_name`, always known since every queued task is a media message) plus a source line: channels/supergroups get a clickable `https://t.me/c/<id>/<msg_id>` link (`message_link()`, only `-100…` ids are linkable — private chats and Saved Messages have no link format and show `#msg_id` instead). `/progress` appends the same link per in-flight download (`register_download(..., link=…)`). Replies render URLs as plain text with `link_preview=False` (no markdown escaping needed).

**Auto-clean subsystem.** `cleanup_loop` runs as a background task; when the interval changes via `/setcleartime`, `CLEAR_TIME_CHANGED` (`asyncio.Event`) is set to wake the loop immediately instead of sleeping the full old interval. `is_cleanup_message` decides what to delete — and **first returns `False` for any real, downloadable media** (`is_downloadable`): whitelist-relayed copies and parse-bot video replies retained in Saved Messages are never deleted, even when their caption contains a douyin/IG URL or a notification prefix. For non-media messages it matches exact command texts, `/setcleartime` commands and replies, any text containing a Douyin URL (the plain-text link *instruction* messages are still cleaned — a web-page-only preview has no file and is not "downloadable"), or text starting with one of the `CLEAN_NOTIFICATION_PREFIXES` — so normal user content is never deleted. The auto-clean task only deletes messages older than `CLEAR_MESSAGE_AGE_MINUTES`, while manual `/clearmsg` has no age limit and deletes the invoking command message last. Note the latency: a message survives up to (interval + age threshold) before auto-deletion (defaults 1 + 1 = up to 2 minutes). Each cycle also runs `cleanup_bot_chat_once()` for the bot menu chat (same interval). `cleanup_saved_messages_once` logs a heartbeat line every cycle even when nothing is deleted, and both cleanups also run once immediately after startup.

**Logging.** A shared logger named `tg_userbot` lives in `log.py` and is configured once at package import (`log.configure(LOG_FILE)`, idempotent) to write to both console and `LOG_FILE` (inside `SAVE_FOLDER`); every module does `from .log import logger`. Progress callbacks log every `PROGRESS_STEP` percent (config.py). Log lines are the primary debugging tool; the startup routine prints instructions on how to verify message reception (expect the "📨 Saved Messages 收到消息" line).

## 磁盘回收：媒体经 CloudDrive2 自动搬到 115（外部配置）

本地磁盘只留最近下载，**已完成的媒体**由 CloudDrive2（CD2，本机 WebDAV 端口 19798）的「备份」任务自动搬到 115 后删本地。这不是本仓库代码逻辑，是 CD2 侧的一次性运维配置，记录如下便于日后对照/排查：

- **备份任务**：源 = `SAVE_FOLDER`（macOS 为 `~/Downloads/Nagram`，CD2 界面里可能把家目录显示成 `/用户名/Downloads/Nagram`，以能看到媒体子文件夹为准）；目标 = `115open/Nekogram`。
- **文件过滤 = 白名单·扩展名**（媒体才搬，运行时文件天然免疫）：
  视频 `mp4 mkv mov avi wmv flv webm ts m4v mpg mpeg 3gp`；图片 `jpg jpeg png gif webp heic bmp tiff`；音频 `mp3 m4a ogg opus flac wav aac`。
- **完成规则 = 删除源文件**（真正释放磁盘的开关）。其余开关务必按此设置，顺序是先配好白名单再开删除源：
  - **删除规则（本地删文件时云端怎么处理）= 保留**。绝不能选「回收站/同步删除」，否则本地任何删除会把 115 上的备份副本一起清掉。
  - 替换规则 = 跳过（或历史版本）；实时监控开启。

安全原理：白名单外的一切（`download_history.txt`、`download_queue.json`、`download.log`、`whitelist_config.json`、`thread_config.json`、`clear_time.json`、`*.download`）不会进入备份 → 没有「完成后」→ 删除源规则不会碰它们。**设计取舍**：zip/rar/pdf 等归档类不在白名单，会一直留在本地（若也转发大量归档，磁盘仍会缓慢增长，需手动加后缀进白名单）。校验过一次真实运行：频道子文件夹的媒体被搬空删净、6 个运行时文件健在。（`Douyin/`、`Instagram/` 是统一下载链路重构前的历史目录，新版本不再写入——抖音/IG 视频现随普通下载落转发来源目录，如 `@DouYintg_bot 显示名/`，仍在 `SAVE_FOLDER` 递归备份范围内。）

**.download 半成品**：中断的下载重启后是「删半成品、整文件重下」，不支持断点续传（见下载模式）。残留的 `.download` 不会被 CD2 搬走。清理由 `clean_temp_files()` 负责，入口有二：`/clean` 命令/bot 菜单「🧹 清理」按钮，以及 **每次启动时 `main()` 会先自动清一次**（此时尚无下载，安全）——自动清理专门兜住异常退出、`/queue del` 后无人认领、或命名逻辑跨版本变化留下的孤儿 `.download`。正常情况下重启能自愈（任务已持久化，重下前删同名 temp）；出现孤儿 `.download` 的成因为：队列任务被移除后旧 temp 无人认领——原消息已删除被自动终结、`/queue del`/`/retry del` 清掉任务，或**命名逻辑跨版本变化**导致重启后算出的最终名与旧 temp 不同（实测案例：无 caption 文件旧版名 `未命名文件 - X.mp4`、新版名 `X.mp4`，旧半成品成死文件）。

**【启动/停止 CD2】bot 菜单按钮**（本仓库代码）：owner 在 bot 私聊主菜单点【🖥 启动CD2】/【🛑 停止CD2】。
- 启动 → `handle_menu_action` 的 `cd2` 分支调 `cd2_start_or_status()`：先 `cd2_is_running()` 对 `127.0.0.1:<port>` 做 TCP 探测，已运行 → 回「✅ 已在运行，无需重启」；未运行 → `cd2_launch()` 用 `start_new_session=True` 脱离本进程组后台拉起 CD2 独立程序（不会随 userbot 退出被连带终止），随后轮询端口约 30s 并回结果；启动输出追加到 `SAVE_FOLDER/cd2_launch.log`。CD2 无内置 stop 命令、未知参数会当普通启动参数（端口被占即自爆退出、不会双开），故停止走信号。
- 停止 → `cd2_stop_or_status()`：`_cd2_pids()` 用 `ps -eo pid=,command=` + **完整路径开头**匹配（`_cd2_pids_from_ps_output`），只命中配置 command 的可执行文件（主进程 + `Start-Service` 子进程），天然避开系统 iCloud 同名进程；对命中 PID 发 SIGTERM 优雅退出，轮询管理端口最长约 20s，仍开放则对余下 PID 补 SIGKILL。CD2 是“主进程 + `Start-Service 子进程`”一主一子结构（监听 19798 的是子进程）——按可执行路径整棵停最稳，不依赖具体 PID。
- 路径/端口/日志目录：CD2 独立程序路径与数据目录都含本机用户名（如 `~/software/clouddrive-2-macos-aarch64-1.0.10/clouddrive`、`~/Waytech/CloudDrive2/log`），属机器相关敏感配置 → 只能放 gitignore 的 `tg_secrets.json` 的 `cd2` 段（`command`/`port`，默认 19798；`log_dir` = CD2 数据目录下的 log，默认空 → 【备份记录】提示未配置），不入代码不入库。
- 【🗂 备份记录】 (`bak`)：读 `log_dir/backup.<日期>.log`，解析 `handle_localfs/cloudfs_notify: delete file and remove from all dests "<路径>"` 逐文件行（即文件已同步到 115、按完成=删除源从本地删除的那一行），过滤成媒体扩展名、按路径去重、时间倒序展示最近 N 条。同一文件因 cloudfs/localfs 双通知会出现两次，须去重；日志无文件大小字段。纯函数 `parse_backup_log_lines`/`read_cd2_backup_records`/`backup_records_text`/`cd2_log_dir` 与 PID 匹配等单测在 `test_menu.py`；端口探测/拉停/拉起/日志读取的真实流程靠实测。
