# 002 下载重试韧性不足：3 次×3 秒耗尽即入榜，无网络恢复自动重放

- **状态**：✅ 已解决（2026-09-10，建议修法 1+2 均已实施；修法 3 作为关联项保留）
- **发现日期**：2026-09-10
- **严重度**：低 —— 不丢任务、不卡死（失败兜底本身正确），但把「网络抖几分钟」放大成「早上一直重试 + 44 条任务堆在 retry 榜等人肉重放」
- **影响范围**：`tg_userbot/config.py`（自动重放常量）、`tg_userbot/queue.py`（退避 + 到期扫描）、`tg_userbot/app.py`（`_retry_sweeper` 后台任务）

## 问题描述

当前下载重试策略：每任务最多 `DOWNLOAD_RETRIES=3` 次尝试，每次失败固定 3 秒后重试，3 连败即转入 retry 榜**永久停靠**，只能等用户手动 `/retry <n>` / `/retry all` / 菜单 ▶️。

当网络链路出现**分钟级**抖动（本次 Hiddify 隧道 2026-09-10 凌晨~早上反复病了三波：00:07–01:27、04:00–04:19、07:43–08:54），后果是：

- 在跑的任务全体 3 连败（每次尝试被 telethon keepalive ~60 秒探活杀掉）→ 当天 110 次 RETRY 事件、110 个任务入榜；
- retry 榜没有任何「网络恢复后自动重放」机制，任务堆到 44 条直到用户人肉 `/retry all`；
- 用户视角就是「一直重试」，且醒来后还要手动救。

## 为什么判它「低」而非缺陷

- 失败兜底方向正确：任务不丢、不卡死、不重复下载（retry 榜 + 启动恢复 + 内容去重三层都在）。
- 网络层取消（future.cancel()）被正确识别为可重试的 ConnectionError，没有误杀。
- 「快速烧完预算进榜」在链路持续差时避免了无限空转，行为本身合理；缺的是**恢复侧**的自动化。

## 核实结论（2026-09-10，Claude Code，基于真实事件流）

数字全部对上，且故障根因是**外部网络**、不是程序：`runtime/task_events.jsonl`（字段名
`ev`/`ts`/`id`）在 9/10 记录 `RETRY 114 / FAILED 114 / RUNNING 162 / SUCCESS 48`；
`download_queue.json` 当时 `tasks=0, retry=44`。342 次失败尝试里 **340 次**是
`ConnectionError: 下载被底层连接取消（网络层 future.cancel()）`。

补充两点原记录没提的：

1. **失败高度成片**（按分钟聚类）：07:43–07:48 一分钟内 26 次、06:49–07:01 共 120 次——
   是同一分钟里多个并发任务同时死，不是零星失败。配合「独立于 worker 池的 bot 菜单客户端
   在同一分钟每 60 秒断连一次」「07:42:37 有 14 条 worker 在同一秒被发现已陈尸池中」，
   共享代理链路被打穿是唯一解释。
2. **retry 榜的 attempts 会跨手动重放累计**：当前 44 条里分布为 `{2: 33, 3: 6, 5: 4, 11: 1}`
   ——有一条被重放到 11 次。所以「入榜」不是终点，反复 `/retry all` 后同一记录会持续累加，
   更加坐实「缺自动恢复侧」这一判断。

## 实际修法（2026-09-10 已实施）

采用「**周期扫描 + 每任务指数退避**」，把原建议的第 1、2 项合并实现（比原案的事件触发更健壮）：

- **为什么不用原案的「下载成功/重连成功后放一轮」**：核实中发现该触发会**漏掉「全卡住」场景**——等所有任务都进了 retry 榜，队列里就没有任务在跑，也就永远不会再有「下载成功」事件；而主客户端 9/10 全天只重连了 4 次（04h×2、07h×1、08h×1），恢复时刻未必伴随重连。结果可能是网络早就好了、榜还躺着等人手动救。故改用「到期即扫」，天然无死锁。
- `next_retry_at = now + min(60s × 2^(attempts-1), 30min)`，失败入榜（`queue_fail_to_retry`）与 retry 内再失败（`queue_retry_failed`）都刷新。
- `app._retry_sweeper()` 每 60 秒调 `queue.replay_due()`；只放到期、非 EXECUTING 的记录。
- **新增两条用户要求的约束**：① `attempts > 10` 不再自动重放，只能手动（`AUTO_RETRY_MAX_TIMES`）；② 每轮最多放「当前空闲 worker 数」条（`DOWNLOAD_WORKER_QUEUE.qsize()`，池禁用时回落 `DOWNLOAD_CONCURRENCY`）——避开并发首轮跨 DC 授权导出竞态（实测 6 路并发 5/6 首轮失败）。
- **手动路径不受约束**：`/retry n`、`/retry all`、菜单 ▶️ 照旧立即执行，不看退避与上限。
- **向下兼容**：旧记录无 `next_retry_at` → 视为已到期，重启后自动重放一轮（自愈）。

单测：`test_queue.py::AutoReplayDueTest`（12 个：退避序列与封顶、两条失败路径写字段、到期/未到期/缺字段/EXECUTING/超上限、空闲 worker 预算与池禁用回落、手动路径不受约束）、`test_retry_sweeper.py`（3 个接线测试）。

## 原建议修法

1. **网络恢复自动重放 retry 榜**（收益最大，优先做）：检测到「主客户端/worker 重连成功」
   或「连续 N 次失败后出现一次成功」后，自动 `/retry all` 一轮（带次数上限防风暴，如每次
   恢复只放一轮）。可选配置开关。
2. **指数退避**：连续失败时间隔拉长（如 3s → 30s → 120s），一次分钟级抖动就不再必然烧完 3 次预算。注意与现有 per-error-kind 上限逻辑（AuthBytesInvalid 竞态放宽）的兼容。
3. **（关联项，来自静态分析报告 Q2，已代码核实为真）失败 worker 无健康隔离**：
   `download.py:881` 在 `finally` 里对所有退出路径一律 `workers.release(worker)`，
   `workers.py:257` `q.put_nowait()` 无任何健康检查，只有 `borrow()` 借出时 `is_connected()`
   验活（挡不住半开连接）。本次事故中**不是**主因（94% 失败死在 ~60s keepalive、看门狗 0 次
   触发、报告 Q3 那条"复用异常 worker 反复超时"的循环未发生——秒级即败的"死连接"特征只占
   9/342），但作为韧性缺口值得与第 1 项一并考虑：失败原因属网络类时在 `release()` 就地
   `disconnect()`（借出时反正会重连），比新增销毁/重建机制更小。

前两项独立可分别实施；第 3 项优先级最低。

## 验收标准

- 模拟「连续失败若干次后网络恢复」：任务应自动重放成功，retry 榜清空，无需人工干预；网络持续差时不会无限重试风暴。

## 发现经过（2026-09-10 排查记录）

排查「今早下载一直重试」：380 次失败尝试 100% 为「下载被底层连接取消（网络层 future.cancel()）」，零逻辑错误；bot 菜单连接（独立客户端）同窗口 ~60 秒一断至 08:54；04:00 段主客户端 IncompleteReadError 连 TCP 都建不起来；好窗口（00:40–01:57 慢速爬完、06:55–07:25 满速 1.2MB/s）零代码改动即恢复正常；同一分钟成败交错（01 时 28 成功 vs 8 耗尽）。结论：根因是 Hiddify 代理链路间歇不稳，非程序缺陷；本 issue 记录的是把抖动放大成体验问题的韧性短板。详见 issues/README.md 背景。
