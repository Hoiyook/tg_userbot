# 001 日志轮转双进程冲突：主 userbot 与 Chrome Agent 共写同一个 download.log

- **状态**：✅ 已解决（2026-09-10，代码已修；**待运维重启两个进程**才生效——见文末）
- **发现日期**：2026-09-10
- **严重度**：中 —— 当前已造成一次真实日志数据丢失（2026-09-09 全天日志被覆盖，不可恢复）
- **影响范围**：`tg_userbot/log.py`（configure）、`tg_userbot/config.py`（import 期 configure）、`tg_userbot/chrome_agent.py`（进程入口）

> **2026-09-10 核实补充（Claude Code）**：本 issue 的机制判断**完全成立**，但「影响范围」里
> 对 `chrome_agent.py` 的描述不准确——该文件里**没有任何 `log.configure` 调用**，它只
> `from .log import logger`。真正挂 handler 的是 `config.py` 末尾的
> `log.configure(LOG_FILE, LOG_RETENTION_DAYS)`，在 **import 包时**执行（chrome_agent
> 因 `from .config import ...` 触发）。这决定了修法：**不能在 chrome_agent 模块级**
> configure（主进程也 import 这个模块——`chrome_client.py:21` 要用它的纯函数，模块级
> configure 会把主进程日志一并劫走），只能在**进程入口**函数里调。

## 问题描述

主 userbot 进程（`tg_userbot_final.py`）与 Chrome Agent 进程（`python -m tg_userbot.chrome_agent`）是两个独立进程，但都调用 `log.configure(LOG_FILE, LOG_RETENTION_DAYS)`，给**同一个文件** `RUNTIME_DIR/download.log` 各自挂了一个 `TimedRotatingFileHandler`（when="midnight"）。

午夜跨天时两个进程**先后各自轮转**，POSIX `os.rename` 会静默替换已存在的目标文件，于是发生：

1. 进程 A 在 00:00 过后首条日志触发轮转：`download.log` → `download.log.2026-09-09`（归档 OK），并打开新的空 `download.log` 继续写。
2. 进程 B 稍后（它只在有日志要写时才检查轮转）也触发自己的轮转：把**进程 A 刚打开的新 `download.log`** 改名成 `download.log.2026-09-09`，**覆盖掉刚归档的 A 文件内容**，再打开一个新的 `download.log` 归自己用。
3. 进程 A 手里的文件句柄仍指向被改名走的那个 inode（文件名已变成 `.2026-09-09`），于是 A 的所有日志从此**持续写进归档名文件**，直到下次轮转。

## 实际损失与现场证据（2026-09-10 排查实测）

- `download.log.2026-09-09` 里 **2026-09-09 的行数为 0**（9/9 18:16 主进程启动后到午夜的日志，包括 Chrome Agent V1 首晚运行日志，全部丢失）；该文件第一行是 `2026-09-10 00:00:46`，且含主进程 9/10 全天 6160+ 行日志。
- `download.log`（当前文件）只有 Chrome Agent 00:30–00:39 的日志，之后主进程日志再没进过它。
- 排查当日问题（早晨下载重试）时，该现象曾直接误导排查方向（主进程日志不在预期文件里）。

## 现场复核（2026-09-10 11:53，Claude Code 实测）

**不是历史事故，当时仍在发生。** `lsof` 显示两个进程的文件句柄正好错位：

```
PID 6391 (tg_userbot_final.py, 启动 9/9 18:16)  FD 3w  inode 35567388 → download.log.2026-09-09
PID 3616 (chrome_agent,      启动 9/9 21:59)  FD 3w  inode 35569456 → download.log
```

即：**主进程在往归档名文件里写，Chrome Agent 占着正式文件名。** 逐秒还原出的时序与上文
预测机制逐字吻合：

| 时刻 | 动作 | 结果 |
|---|---|---|
| 9/10 00:00:46 | 主进程首次写日志 → 轮转（rolloverAt=9/10 00:00，归档名取 9/9） | 含 9/9 全天内容的当前文件 → `.2026-09-09`；开新 `download.log` 并写入首行 00:00:46 |
| 9/10 00:30:02 | Chrome Agent 首次写日志（`📋 认领 Chrome 任务`）→ 同一归档名轮转 | 把刚归档的 `.2026-09-09`（9/9 内容）**覆盖**；自己开新 `download.log` 写 00:30–00:39 |
| 00:30 之后 | 主进程句柄仍绑在被改名走的 inode | 主进程当天全部日志持续灌进 `.2026-09-09`（00:00:46 → 11:52:49 共 7197 行） |

佐证：`grep -c "^2026-09-09"` 对 `download.log` 及全部 4 个归档文件**合计 0 行**——9/9 全天
日志无一幸存（因主进程 9/9 18:16 才启动，该文件本来就只有 18:16–23:59，所以"晚间丢失"
实为"当天全丢"，比原描述更严重）。`download.log` 当时仅存 Chrome Agent 那 20 行。

## 实际修法（已实施）

1. `config.py` 新增 `CHROME_AGENT_LOG_FILE = RUNTIME_DIR/chrome_agent.log`。
2. `chrome_agent.py` 新增 `configure_agent_logging()`，**在 `agent_main()` 入口第一行调用**
   （不是模块级——主进程也 import 本模块，模块级会把主进程日志一并劫走）。
3. `log.configure()` 顺手修掉一个连带问题：原来 `logger.handlers.clear()` **不关闭**旧
   handler，被摘掉的文件 handler 直到进程退出都持着旧文件 FD——Agent 重定向后仍一直握着
   `download.log` 的句柄，正是本次要切断的耦合。改为逐个 `removeHandler` + `close`。

测试：`tests/test_chrome_agent.py::AgentLogIsolationTest`（5 个）——路径互异、重定向后
`current_log_path()` 指向 Agent 文件、探针日志只进 Agent 文件且 `download.log` 字节数不变、
重定向后不残留 `download.log` 的 handler、`agent_main` 入口确实调了这个函数（防"函数在但
没人用"）。全量回归：改动前 503 用例 / 3 失败 / 14 错误 → 改动后 508 用例 / **同样** 3 失败
/ 14 错误（既有失败与本次无关）。

## 待运维执行（代码改完也**必须重启**才生效）

代码修改无法影响已在运行的进程——主进程的句柄还绑在归档 inode 上，Agent 还在写
`download.log`。需重启**两个**进程：

1. 重启主 userbot（`TG_PROXY=socks5://127.0.0.1:12334 .venv/bin/python tg_userbot_final.py`）。
   重启后 handler 重新挂到 `download.log`；该文件 mtime 是今天，故当天不会再触发轮转，
   新日志正常落 `download.log`。
2. 重启 Chrome Agent（`/chrome_stop` → `/chrome_start`）。**必须一起重启**：否则次日
   00:00 老 Agent 仍会按旧代码轮转，冲突复发。

**遗留文件处置**：现被错误命名为 `download.log.2026-09-09` 的文件（内含 9/10 当天主进程
日志）不会被自动覆盖——主进程重启后归位到 `download.log`，9/11 00:00 轮转产生的是
`.2026-09-10`（归档名按 rolloverAt 前一日算），两者不撞名，内容可安全留存至 7 天保留期
被裁掉。`stats._log_files_for`（`stats.py:132`）按**行首日期前缀**过滤内容，所以该文件
在 3 天/7 天窗口里仍能被正确计入 9/10；但**今日窗口读不到**——它只找
`download.log.2026-09-10`。今日台账以 `task_events.jsonl` 为主数据源，影响仅限旧关键词
回落口径；如需保留可在重启前手工改名（注意别改成 `.2026-09-10`，会被 9/11 的轮转覆盖）。

## 验收标准

- 主进程与 Chrome Agent 同时运行跨午夜，次日两个日志文件各自完整、互不覆盖，归档文件含正确的当天内容。
