# 下载白名单双通道扫描制改造 —— 设计规格书

日期：2026-09-13
状态：设计已经用户逐节确认（方案 A：事件生产者化 + 扫描补漏双通道；DB 不可用回退直下）
前置阅读：`CLAUDE.md` 的「标签监听」「Download whitelist (unified relay)」两节，以及
`docs/plan/Telegram标签监听_Producer-Consumer_SQLite架构调整_DeepSeek开发任务书.md`。

## 1. 背景与目标

userbot 不是长期启动的：进程停机期间白名单聊天里发的媒体，事件监听永远收不到，
就永久漏掉。本改造把白名单中转改到标签监听已验证的 Producer/Consumer 机制上：

- **在线实时**：事件监听保留，但瘦身为「生产者」——只把媒体记成持久化任务，不转发；
- **停机补漏**：新增白名单扫描生产者，按消息 id 推进 checkpoint，补上停机缺口；
- **统一执行**：转发/下载由现有 `listener_worker` 受控执行（单并发 + 节流 + FloodWait 全停 + 租约）；
- **自主回补**：用户可对单个聊天自设初始消息 id（`/wl since`），把停机漏掉的存量补回来。

### 设计原则（不变项）

- **配置独立性**（CLAUDE.md 头号约束）：`whitelist_config.json`（/wl）与 `listen.json`
  （/listen）仍是两条独立配置源，互不推导。本改造共享的是**任务存储与执行**，不是配置。
- Saved Messages 原件路径（`_enqueue_me`）、命令分发、抖音/IG 链接解析、标签监听、
  评论跟进、下载队列/去重/命名全链路**一律不动**。
- §14 重叠判定保留：白名单聊天上的监听规则不再建收藏夹任务（现在另有唯一索引结构性兜底）。

## 2. 总体架构

```
whitelist_config.json（/wl，配置源不变）
   ├─ 事件生产者【在线实时】白名单 chat 媒体事件 → 记任务（origin=wl）
   └─ 扫描生产者【停机补漏】按 wl 游标周期扫描 → 记任务（origin=wl）

listen.json（/listen，配置源不变）
   ├─ Scanner 标签命中 → 记任务（origin=listen）
   └─ follow_scan 评论跟进 → 记任务（origin=listen）

        listener_tasks（SQLite，唯一索引跨链路去重）
                    │
        listener_worker（单并发 + 1.5s 节流 + FloodWait 全停 + 租约）
                    │ 转发收藏夹 → enqueue_media(src=origin) → 现有下载队列
```

两条生产来源写入同一张任务表，唯一索引
`(source_chat_id, message_id, target_type, COALESCE(target_chat_id, 0))` 使
「同一消息的收藏夹任务只存在一条」跨链路成立：事件链与扫描链并发生产同一单元时，
后到者被 `INSERT OR IGNORE` 吃掉，**双转发在结构上不可能**。扫描链天然是事件链的
兜底——事件漏了（断线窗口/进程崩溃），下一轮扫描按游标补上。

## 3. 数据模型（schema v2 → v3）

### 3.1 listener_checkpoints 加 chain 列

新主键 `(source_chat_id, chain)`，chain ∈ {`listen`, `wl`}。同一聊天两边都在时
两条游标独立推进：`/wl since` 回补只倒退 wl 游标，不影响监听游标；监听扫描与
白名单扫描各自读自己的游标。

迁移：重建表（新建 → 复制旧行并填 `chain='listen'` → 删旧 → 改名），幂等可重跑。

### 3.2 listener_tasks 加 origin 列

`origin TEXT NOT NULL DEFAULT 'listen'`，迁移时旧行全部回填 `listen`；wl 生产者
写入 `origin='wl'`。用途：

- Worker 入队副本时显式 `src=task["origin"]`——顺带修正一个既有偏差：今天白名单
  转发副本入队时 `src` 被推断成 `me`（`queue.enqueue_and_start` 按 `chat_id==MY_ID`
  推断），台账「📥 输入事件」的中转桶一直数不准，改后数准。
- `/listen` 视图与 `📡 标签监听` 台账分节的任务统计按 `origin='listen'` 过滤；
  `/wl` 视图显示 `origin='wl'` 的存量（`get_listener_stats` 参数化 origin）。
- claim 排序用（见 §6.2）。

唯一索引不变。`enqueue_listener_tasks` / `get/set_listener_checkpoint` 等函数加
chain/origin 参数，缺省值保持旧语义（测试改动最小）。

## 4. 事件生产者（app.py 改造）

`new_message_handler` 的白名单媒体分支从 `relay_chat_media(...)` 改为
`record_whitelist_media(message, chat_id, source_override)`（新函数，`asyncio.create_task`
照旧）。生产逻辑：

### 4.1 单条媒体

1. `dedup.should_skip`（该消息的 `media_keys`）命中 → 不建任务，记日志返回
   （今天的行为是「转发后下载侧拦截」，改后连转发都不做；`/dedup off` 全放行）。
2. `resolve_origin_snapshot(message)`（评论继承，从源消息解析，一次）。
3. 复用 `listener._build_tasks(chat_id, [message], {("saved_messages", None)}, True,
   消息自身文本, message.id, origin)` 组任务记录。
4. `runtime_db.enqueue_listener_tasks(chat_id, records)`（不带 checkpoint——游标是
   扫描链的事）。

### 4.2 相册（grouped_id 非空）

保留攒批协调器形态，但产出从「一次 forward」变成「一条任务」：

1. 成员事件登记进 `(chat_id, grouped_id)` 协调表；首个成员起任务，睡 1.5s 攒批；
2. `_fetch_album_members` 权威成员拉取（现有函数照用）；
3. caption = `pick_group_caption_text(members, gid)`；origin =
   `resolve_origin_snapshot(members[0])`（整组一次）；
4. dedup 前置：**整组全部成员**的 media_keys 都命中才跳过（部分命中照建任务，
   下载侧 per-copy 拦截）；
5. 建一条任务（anchor=组内最小 id，`member_ids` 进 payload），协调表保留 5s 宽限
   防迟到成员重复建（唯一索引双保险）。
6. 权威列表拉不到：用已登记成员建任务（媒体不丢）；缺失成员由扫描链按游标补。

### 4.3 DB 不可用回退（用户已确认）

`runtime_db.DbUnavailable` → 该媒体**回退直下**：`enqueue_media(message, chat_id,
source_override=source_override)`（不转发、无收藏夹副本、dedup 照常）。媒体不丢，
只丢副本。**不保留第二套转发代码**。扫描链此时同样不可用，属整体降级，恢复后
扫描从游标补漏（回退直下发生在游标推进之前——wl 游标没动，DB 恢复后扫描会再
建任务；dedup 拦住重复下载，多出一份收藏夹副本是可接受的代价）。

### 4.4 删除清单

`relay_chat_media` / `_relay_single` / `_forward_to_me` / `_relay_album_member` /
`_relay_album_group` / `_forward_album_to_me` / `_fallback_relay_each` / `_ALBUM_RELAY`。
**保留** `_maybe_album_caption` / `_fetch_group_caption` / `_ALBUM_CAPTIONS`
（`_enqueue_me` 的 Saved Messages 原件路径还在用）。

## 5. 扫描生产者（whitelist scan）

新后台循环 `app._whitelist_scan_loop()`（与 `_listener_loop` 并列，`main()` 创建并
纳入取消清单）：

- 启动门槛：`RUNTIME_DB_READY`；每轮照常运行（**不跟随 `LISTEN_ENABLED`**——白名单
  没有总开关概念，`/wl del` 移除聊天即停）。
- 每轮重新遍历 `state.WHITELIST_CHATS`（`/wl add/del` 即时生效，无需重启）。
- 每聊天按 `chain='wl'` 游标 `_fetch_new`（复用 listener 的取消息函数：limit=200、
  min_id=游标、reverse=True、补齐边界相册）。
- 命中条件 = **可下载媒体**（`is_downloadable`），无标签匹配；纯文本跳过、游标照推。
- **不跳过镜像帖**（`is_channel_mirror` 只在监听扫描用）：白名单契约是「这个聊天的
  一切媒体都要」。
- checkpoint 缺失时就地初始化为当前最新 id（不扫历史，§17 同款纪律）；读不到最新 id
  记失败、下轮再试。
- 相册按 grouped_id 整组一个单元（复用 `group_by_album` + `_build_tasks`）；
  dedup 前置同 §4.2；origin 快照同款。
- 任务与游标**同事务**推进（`enqueue_listener_tasks(..., checkpoint=processed_upto)`），
  背压语义照旧：待执行 ≥ `LISTEN_MAX_PENDING_TASKS`(1000) 时停扫、游标不动。
- **分页上限**：每轮每聊天最多 `WHITELIST_SCAN_PAGES_PER_ROUND`(10) 页 × 200 条，
  页间睡 `WHITELIST_SCAN_PAGE_SLEEP_SECONDS`(5s)——几千条积压摊到多轮读。
- 死聊天降噪：某聊天连续扫描失败只报第一次 ERROR，之后静默退避直到成功。
- 周期 `WHITELIST_SCAN_INTERVAL_SECONDS`(300s)（在线时事件兜实时，扫描只管补漏）。

新配置常量进 `config.py`：`WHITELIST_SCAN_INTERVAL_SECONDS` / `_PAGES_PER_ROUND` /
`_PAGE_SLEEP_SECONDS`（页大小直接复用 `LISTEN_MAX_MESSAGES_PER_SCAN`）。

## 6. Worker 改动（listener_worker.py）

### 6.1 src 与禁转回退

- `_enqueue_copy(..., src=task["origin"] or "listen")`。
- `ChatForwardsRestrictedError`（来源禁转）加入 `_PERMANENT_ERRORS`。永久转发失败
  且 download=1 时：回退 `enqueue_media(原消息, chat_id, source_override=payload
  快照 source_name 或聊天标题)`——保住今天「来源禁转也能拿到文件」的行为；任务标
  **FAILED**，错误文案注明「已回退直下原消息（无收藏夹副本）」。取不回源消息
  （已删除）仍按今天的语义直接 FAILED，无回退。

### 6.2 claim 优先级：listen 优先于 wl

claim SQL 的排序从 `ORDER BY id` 改为
`ORDER BY (origin='wl'), id`（SQLite 布尔假值在前）：监听任务是稀疏的时效性命中，
优先消费；wl 存量（尤其回填批次）排后面。监听任务流量稀疏，不会饿死 wl 队列；
wl 实时任务最多多等几条监听任务（秒级）。

## 7. 命令与菜单

- **`/wl since <聊天> <消息id>`**：回补入口。聊天可为列表序号 / @用户名 / 数字 ID；
  消息 id 须为正整数。校验聊天在白名单后把 wl 游标写为该 id（扫描处理其**后**的
  消息，min_id 语义不含本身），随即触发一轮即时扫描。id 比当前最新还大时不报错
  （自然扫不到东西）。
- **`/wl scan`**：立即扫一轮（重入保护 `_WL_SCANNING` 与监听的 `_SCANNING` 分开）。
- `/wl` 列表视图每行加「已扫至 #<id>」与该聊天待执行任务数；末尾加 since 用法提示。
- 菜单【📋 白名单】加「⏪ 回补」按钮：复用输入窗口模式（`bot.open_input_window`
  统一互斥），窗口内一行「<序号|@user|id> <消息id>」。
- `is_wl_command` 正则照旧覆盖新子命令形态。

## 8. 风控汇总

| 防线 | 机制 | 来源 |
|---|---|---|
| 转发速率 | 单并发 + 最小间隔 1.5s | 既有 worker 纪律 |
| 服务端限流 | FloodWait 采信返回值并暂停整个 Worker | 既有 |
| 队列背压 | 待执行 ≥1000 停扫、游标不动 | 既有 |
| 读请求摊开 | 每轮每聊天 ≤10 页 ×200 条、页间 5s | 本改造新增 |
| 重复内容 | 建任务前置 dedup（整组全命中才跳） | 本改造新增 |
| 补漏延迟 | 扫描周期 300s，在线时事件兜实时 | 本改造新增 |

已知代价：回填 3000 条 ≈ 多轮扫描 + 按 ~2s/条受控转发，全程约 1.5~2 小时——
摊开正是风控要的，不是缺陷。

## 9. 兼容与迁移

- schema v2→v3 迁移如 §3（幂等可重跑）；`RUNTIME_DB_SCHEMA_VERSION` 升 3。
- wl 链首扫 checkpoint=最新（不扫历史）；存量缺口由用户显式 `/wl since` 回补。
- `/wl del` 后该聊天的存量任务照执行完（Worker 不读配置，§12 纪律）。
- 台账：`📡 标签监听` 分节任务统计改 origin='listen' 口径；「📥 输入事件」中转桶
  改由 src='wl' 数准；新增 wl 任务存量展示进 /wl 视图（不新增独立台账分节）。
- CLAUDE.md 更新：Overview 第 4 条、Architecture 白名单段、标签监听段的 §14 表述、
  模块索引（app.py/listener/listener_worker/runtime_db 职责）、并发模型、
  「标签监听配置指引」表加 wl 链配置行。

## 11. 已知边界

- 事件与扫描的实时差：在线媒体经 Worker 轮询（2s）+ 节流（1.5s）≈ 3~4s 落转发；
  抖音/IG 解析 bot 回帖同此延迟（可接受，已确认）。
- 回补只覆盖 `/wl since` 指定 id 之后的存量；更早的仍拿不到（Telegram 按 id 前进）。
- DB 不可用窗口内的白名单媒体走直下回退，没有收藏夹副本；DB 恢复后扫描可能对同一
  消息再建任务（游标未推进），多出一份副本、下载由 dedup 拦（§4.3 已述）。
- Worker 单并发是全链共享的：监听命中与白名单媒体互相排队（listen 优先）。
