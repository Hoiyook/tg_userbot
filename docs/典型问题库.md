# 典型问题库与控制措施

> 2026-11-16 建立。素材：仓库 391 个提交中的 **139 个修复类提交** +
> 两轮全面架构审查 + 两轮五需求冲刺 + 2026-11-13 巡检报告。
> 目的：把反复出现的缺陷**模式化**，每类配上控制措施——自动化守卫为主、
> 人工纪律为辅，把同类事故的复发概率压到最低。

## 一、八大重复缺陷模式（按复发频率排序）

### P1. 静默死亡——失败被吞/被伪装（复发 9+ 次，最高危）

**模式**：出错时不抛、不响、不记——功能"看起来存在"，实际没有任何效果。
用户感知是"点了没反应"，从发生到发现平均以天计。

| 案例 | commit | 具体形态 |
|---|---|---|
| f2 枚举 403 三轮耗尽后静默 return，伪装成"没有符合条件的作品" | e617b42 | 错误遮蔽 |
| /chrome_failed 静默无回复（updated_at 类型炸排序 + 顶层无兜底） | 6813bd0 | 异常上抛无兜底 |
| 面板 FloodWait 罚等被 shielded 内层吞掉，外层分支永远收不到 | a661401 | 异常在内层被吞 |
| 重排队任务旧 notified_at 吞掉新一轮终态——不通知、不记台账 | be817a5 | 陈旧标记跳过 |
| 看板 JS 语法错误 ×2，整页按钮全部坏死 | 87dca05 / 80ec775 | 前端静默死亡 |
| /pixiv 重排队回执 label 未定义（NameError），回执静默死亡 | be817a5 | 未定义名 |
| /memo dispatch 从未接线（8d390e4 声称接线但缺失） | a01b208 | 声称≠事实 |
| CDP target_id 未赋值引用，把真实失败吞成协议错误 | 57f9a06 | UnboundLocalError |
| 回放拦截把重启间隙 4 条 /paw_plan 静默拦成 ⏸"没跑也找不到"；/cmdq confirm 再执行时再次撞拦截，闸门只进不出 | 28332d4 | 声称≠事实：确认出口未接通 |

**为什么反复发生**：Python 的 except 吞异常是合法语法；前端 JS 无任何
编译/测试门槛；"加个功能"的提交往往不带失败路径的测试。

**控制措施**：
- ✅ `tests/test_undefined_names.py`（pyflakes 全包扫描）——已抓到 pixiv label
- ✅ `tests/test_dashboard_js.py::DashboardJsSyntaxTest`（node --check）——JS 语法错误进不了主干
- ✅ chrome 命令顶层兜底（handle_chrome_command 拆 inner + 兜底回 ❌）
- ✅ `tests/test_cmdq.py`——confirm 出口有测试钉死；回放拦截必发 TG 通知；
  重启间隙的现发指令（≤15 分钟）新鲜度豁免直执行
- 📋 纪律：**每条用户可见路径必须有"失败也说话"的测试**——修 bug 时顺手给失败路径补断言

### P2. 无超时的等待——单点挂死拖垮全局（复发 3 次，损失最大）

**模式**：对网络/子进程的某个操作没有超时，一旦对端半死就永久挂起；
如果是串行链路，持锁挂死会饿死整条队列。

| 案例 | commit | 挂死时长 |
|---|---|---|
| CDP WebSocket send 无超时（recv 有保护、send 没有）——agent 停摆 | fb8302a | **12 小时** |
| /dyu 转交 send_message 无超时，串行锁被拖死，后面 80 个任务饿死 | 895fe37 | 1.5 小时 |
| /paw_plan 触发 20MB 全量刷新（4 连败 × 120s），命令无响应 | 7f9c32c | 20 分钟 |

**为什么反复发生**：库默认"永不超时"是常态；只测正常路径，半死连接
（TCP 半开、CF 盾跳转）只在生产出现。

**控制措施**：
- ✅ CDP send 15s 超时已修；bot 发送 60s 硬超时已修；解析只读缓存已修
- 📋 纪律：**每一个 `await 外部调用` 都要能回答"最坏等多久"**——回答不了就是隐患。code review 时按此问一遍。
- 📋 串行链路（持锁/单 worker）里的任何调用超时必须 **< 队列健康阈值**（如 QUEUE_BACKLOG_WARN_RETRY=50 对应的时长）

### P3. 双入口漂移——面板与 bot 只改一边（复发 4+ 次）

**模式**：同一能力有两个入口（bot 命令 / 面板按钮），改动只落一边；
或者注释声称"对面没有此功能"但事实早已变化。

| 案例 | commit | 漂移内容 |
|---|---|---|
| chrome RETRY_WAIT 面板归"排队中"无操作入口；bot /chrome_failed 可重试可取消 | 7822202 | 归桶+操作不一致 |
| x/pixiv 失败条目无操作按钮（注释称"站点侧没有重试命令"已过时） | 7822202 | 面板弱于 bot |
| CD2 子菜单合并时只收进"停止"漏了"启动" | 0a414e8 | 按钮缺失 |
| 链接分流三入口各自实现语义漂移 | a9bb938 / 7075191 / d610965 | 架构级收敛（单点化+routing.classify 共用） |

**为什么反复发生**：两边代码物理分离；没有"改动 A 必查 B"的机械提醒。

**控制措施**：
- ✅ 架构上已单点化：链接分流（routing.classify 三入口共用）、chrome 取消/重试（request_cancel / retry_request_for 两边共用）、失败清单（failed_tasks 供 /chrome_failed 与 /chrome_retry 同源）
- ✅ `tests/test_dashboard_js.py::DashboardActionWhitelistGuardTest`——hint 模板命令必须在 command_registry 注册
- 📋 纪律：**同款纪律注释**（已在 request_cancel / retry_request_for / failed_tasks 落地）："命令与按钮共用此函数——终态复核、写失败处理、回执文案必须两边一致，否则迟早只改一边"。新增双入口能力时，服务函数先行，两边薄封装。

### P4. 陈旧状态/缓存语义——旧标记吞新事件（复发 4 次）

**模式**：为幂等/缓存引入的"已处理"标记，在对象**重新进入生命周期**时
没有相应失效——新一轮结果被旧标记吞掉；或按数组位置当时间语义。

| 案例 | commit | 具体形态 |
|---|---|---|
| 重排队后旧 notified_at 吞新一轮终态（11-14/15 三条 + 9-24 九条漏记） | be817a5 | 标记不随生命周期失效 |
| requests 台账裁剪按数组位置——刚通知的记录被当最老裁掉 | b23b63c | 位置当语义 |
| done 桶显示最老记录（排序键错） | 45ad3de | 位置当语义 |
| creators 缓存 41 天 stale 腐烂不可见 | 7de16a6 | 缓存年龄不可观测 |
| **监听规则只存 67B JSON 单点**——被清空即永久丢失（停摆 6 天），无 DB 兜底、无告警 | 51f0982/待提交 | 单点真相源 + 丢失不可见 |

**控制措施**：
- ✅ 生命周期失效：任务回非终态即清 notified_at（clear_notified + notify 循环自愈）
- ✅ 语义键排序：_prune_requests 按 notified_at 排序 + mark_notified 挪尾（同秒不受稳定排序影响）
- ✅ 缓存年龄可观测：creators_refresh_ok_at/fail_at 落 schema_meta + 7 天告警行
- ✅ **配置类数据必须入库**（schema v24 listener_rules 起步）：JSON 降级为导出/导入接口，DB 是真相源——任何单点覆写都可从另一层恢复；维护报告加三层一致性哨兵（DB/内存/JSON 计数对照）
- 📋 纪律：**引入任何"已处理"标记时，同时回答"对象重新进入生命周期时谁来清它"**——回答不了就不要引入。

### P5. 资源泄漏/清理缺失（复发 4 次）

**模式**：拿到资源（tab/连接/锁/内存字典）只在 happy path 用，异常路径
与生命周期结束点不归还。

| 案例 | commit | 泄漏物 |
|---|---|---|
| iwara 解析完页面 tab 留着不管，每个任务漏一个 | 57f9a06 | CDP tab |
| 直链 httpx 连接池不显式 aclose | b78f4d7 | 连接池 |
| PROGRESS_SEEN 成功路径不清理 | b78f4d7 | 内存字典 |
| 幽灵租约：领取后被 SIGKILL，租约永不过期任务永久卡死 | bd251bc |  DB 租约 |

**控制措施**：
- ✅ tab：解析完成/失败都立即 close + finally 判空；agent 启动清遗留 tab 兜底
- ✅ 租约：运行期周期回收过期租约
- 📋 纪律：**try/finally 成对检查**——任何 `open/assign` 之后问"异常路径谁释放"。pyflakes 不抓这个，靠 review。

### P6. 竞态/时序假设（复发 5 次）

**模式**：对"谁先谁后"做了未验证的假设——两个写者并发写同一文件、
下游动作快过上游、有效期短于排队时长。

| 案例 | commit | 假设被打破 |
|---|---|---|
| retry 与挂起取消请求的竞态（重试后又被旧取消打回） | fb8302a | 请求应用顺序 |
| iwara 命名竞态——CD2 "3 秒备份删源"赢过 rename | 4a87653 | 本地改名先于云端收走 |
| Pawchive temp_url 6h 有效期 vs 排队时长，超窗即 403 | ce586f4 | 排队时间 |
| CD2 异步上传深层目录落定超 60s 对账窗口 | 2b779c4 | 上传落定时间 |
| 提交认领竞态（本任务已进 tasks 导致排队位次多算） | 5ab14f8 | 认领周期 |

**控制措施**：
- ✅ retry 提交时 remove_cancellation 清挂起取消；apply_retrials 跳过已清条目
- ✅ 命名改 download= URL 参数预命名（不赌本地改名速度）
- ✅ 对账窗口逐轮加倍封顶（15→120s × 9 轮）
- 📋 纪律：**涉及两个写者/两段时序的改动，必须写一个"先 A 后 B 再 A"的测试**；有效期类问题问"最坏排队多久"。

### P7. 环境漂移/版本耦合（复发 3 次，杀伤面大）

**模式**：依赖的隐式契约被上游变化打破。

| 案例 | commit | 漂移 |
|---|---|---|
| **测试进程无兜底隔离 → /listen off 把生产 listen.json 清空，评论区跟进停摆 6 天**（owner 11-16 发现）| 待提交 | 测试/生产同机同仓 |
| httpx 0.28 移除 proxies= 炸 f2；0.25 缺 proxy= 炸 wnacg——锁 0.27.2 | 7bb62a2 | 依赖版本 |
| f2 0.0.1.5 对 Argus 403——升 0.0.1.7 + --no-deps | 7bb62a2 | 上游行为 |
| RAR5 新格式解压全 0 字节残骸（静默假成功） | d4ea0ed | 文件格式 |

**控制措施**：
- ✅ requirements.txt 锁定 + f2 --no-deps 隔离
- ✅ conftest.py 路径隔离兜底（pytest 先于一切业务 import 设 TG_SAVE_FOLDER——config 的路径常量在首个 import 时冻结，单测文件各自设置救不了"别人先 import"的顺序问题）
- ✅ RAR 双引擎 + 静默失败守卫（成品非空校验）
- 📋 纪律：**升级/新增依赖前跑全量测试 + 一条真链路冒烟**；"成品文件必须非空"这类守卫是防假成功的最后闸。

### P8. 观测性缺失——bug 长期不可见（放大一切模式）

**模式**：不是根因，而是"发现时间 × N"的放大器。

| 案例 | commit | 不可见的东西 |
|---|---|---|
| backfill 全程零日志——被下载并发饿死无人知 | f916106 | 吞吐 |
| creators 缓存腐烂不可见 | 7de16a6 | 缓存年龄 |
| 断连风暴/重启频率（巡检才发现） | f5f34c3 | 系统健康 |
| SSE 断连页面冻结，用户看到假状态无提示 | 57f9a06 | 前端连接状态 |

**控制措施**：
- ✅ 每日维护报告（备份验证/裁剪/凭据/磁盘）推 TG
- ✅ 队列积压哨兵 + 卡死哨兵 + 失败报告指纹去重
- ✅ 面板断连横幅 + lastRefresh 时间戳
- 📋 纪律：**新后台循环必须有"活着"的证据**（周期日志/哨兵/面板条目），零日志的循环等于不存在。

## 三、新改动上线前 Checklist（人工纪律，review 时逐条问）

1. **失败路径**：这条路径失败时用户看到什么？有没有测试断言失败也说话？（P1）
2. **最坏等待**：每个 await 外部调用，最坏等多久？串行链路里它会拖死谁？（P2）
3. **双入口**：改了 bot 命令就查面板对应视图/按钮，反之亦然；新能力服务函数先行、两边薄封装。（P3）
4. **标记生命周期**：新引入的"已处理"标记，对象重进生命周期时谁来清？（P4）
5. **资源归还**：open/assign 之后，异常路径和结束点谁释放？（P5）
6. **时序假设**：两个写者/两段时序，最坏顺序是什么？有没有测试钉住？（P6）
7. **依赖契约**：动依赖前全量测试 + 真链路冒烟。（P7）
8. **存活证据**：新后台循环的"活着"证据是什么？（P8）

## 四、复发时怎么办

1. 按 `git log --grep fix` 定位是否**同模式复发**（对照本库八大模式）；
2. 复发 = 该模式的控制措施有缺口 → **先补防线再修 bug**（守卫测试先行）；
3. 新模式 → 追加到本库（模式描述 + 案例 commit + 控制措施），并评估能否自动化；
4. 每次全量架构审查（建议季度）重读本库：删掉已绝迹的模式、合并重复模式。

## 五、本库的保鲜机制（2026-11-16 建）

问题库和守卫测试本身也会腐烂——腐烂路径与对应触发器：

| 腐烂路径 | 触发器（自动化） |
|---|---|
| 引用的测试文件被改名/删除/移动 | `tests/test_typical_issues_doc.py`：防线清单表格里每个 `tests/…py` 必须存在 |
| 引用的 commit hash 写错/历史重写 | 同上：每个 hash 必须 `git cat-file` 可查 |
| 新增守卫但文档没更新（防线清单过期） | 同上：测试 docstring 的 `P<n> 控制/模式` 标记 ⊆ 文档 P1~P8 段落 |
| "复发时追加"的承诺无人执行 | `maintenance.py`：schema_meta 记 `issues_doc_reviewed_at`，超 90 天未整理在每日维护报告喊 ⚠️ |
| 守卫静默失效（结构变了但测试绿） | 守卫自带"结构变动即失败"断言（如 hint 扫描 `assertTrue(hints, "结构变动？")`） |

**整理约定**：修完一个复发缺陷、或每 90 天（维护报告会提醒），重读本库，
在 `schema_meta.issues_doc_reviewed_at` 登记整理日期（初始 2026-11-16）。
其他时间点类文档（巡检报告等）是快照，天然过期，**归档不保鲜**——
保鲜只针对"活文档"（本库、操作手册）。
